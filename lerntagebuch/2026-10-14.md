# Lerntagebuch – 2026-10-14

## 1046. Last Stone Weight (Easy)

- **Muster:** Max-Heap / Priority Queue (wiederholt das größte Element entnehmen und Ergebnisse zurückschieben); Alternative: Counting-Array bei kleinem Wertebereich
- **Hinweisstufe benötigt:** 1 (allgemeine Klarstellung, was ein Heap garantiert und dass man nur über `push`/`pop` arbeitet, nicht selbst Knoten platziert; den Ablauf mit `pop`, `pop`, `push` hat er danach selbst formuliert. Bei der Alternative führte die Leitfrage „Kann der schwerste Stein schwerer werden?“ zum nur nach links wandernden Index.)
- **Komplexität:** Zeit O(n log n), Speicher O(n) (Aufbau per `BinaryHeap::from` in O(n)); Alternative Counting-Array: Zeit O(n + W), Speicher O(W) mit W = 1000
- **Status:** lokale Tests grün, Einreichung offen
- **Wiederholen am:** 2026-10-17, dann 2026-10-21, dann 2026-11-14

### Aufgabe

Gegeben ist ein Array `stones` mit Steingewichten. Pro Runde werden die zwei schwersten Steine `x <= y` zerschlagen: Bei `x == y` verschwinden beide, sonst bleibt ein Stein mit Gewicht `y - x`. Am Ende bleibt höchstens ein Stein übrig; zurückgegeben wird sein Gewicht oder `0`, falls keiner übrig ist.

**Constraints:** `1 <= stones.length <= 30`, `1 <= stones[i] <= 1000`

Beispiele: `[2,7,4,1,8,1]` → `1`, `[1]` → `1`, eigener Randfall `[3,3]` → `0`

### Kernidee (eigene Worte)

> Klassische Verwendung eines Heaps. Die größten Elemente sind immer oben im Heap und können von dort genommen und verarbeitet werden. Das Ergebnis geht wieder zurück in den Heap und wird passend einsortiert.

**Schärfung:** Garantiert ist nur, dass das *eine* größte Element oben liegt, der Rest ist nicht sortiert. Das zweitgrößte bekommt man, weil der Heap nach jedem `pop` seine Eigenschaft selbst wiederherstellt. Auch „einsortieren“ heißt nicht sortieren: `push` stellt nur die Heap-Eigenschaft (jeder Knoten ≥ seine Kinder) in O(log n) wieder her.

### Weg zur Lösung

1. **Erster Gedanke:** Array sortieren und von groß nach klein abarbeiten. Das Problem ist das Wiedereinfügen der entstandenen kleineren Steine.
2. **Missverständnis zum Heap:** Nach dem Wikipedia-Artikel die Vorstellung, man müsse das Ergebnis selbst an eine Stelle im Baum setzen und damit die Ordnung kaputt machen. Klarstellung: Man arbeitet nur mit `push`/`pop`, die Ordnung erhält der Heap selbst.
3. **Ablauf selbst formuliert:** zweimal `pop`, Differenz `push`en, solange mehr als ein Stein da ist. Bei Gleichstand wird nichts zurückgeschoben, und ein leerer Heap ergibt 0.
4. **Komplexität:** zuerst O(log n) geschätzt, also die Kosten einer Operation mit den Gesamtkosten verwechselt. Durch Zählen der Operationen (n `push`es, höchstens n Runden) kam er auf O(n log n).
5. **Alternative:** Gewicht als Index in einem Zählarray. Da der schwerste Stein nie schwerer wird, wandert der Suchindex nur nach links, insgesamt also O(n + W).

### Meine Lösung

Erste Fassung (Tests grün):

```rust
impl Solution {
    pub fn last_stone_weight(stones: Vec<i32>) -> i32 {
        let mut heap: BinaryHeap<i32> = BinaryHeap::with_capacity(stones.len());
        for s in stones.into_iter() {
            heap.push(s);
        }
        while heap.len() > 1 {
            let val1 = heap.pop().unwrap();
            let val2 = heap.pop().unwrap();
            heap.push(val1 - val2);
        }
        if let Some(ans) = heap.pop() {
            ans
        } else {
            0 as i32
        }
    }
}
```

Endfassung nach dem Review:

```rust
impl Solution {
    pub fn last_stone_weight(stones: Vec<i32>) -> i32 {
        let mut heap: BinaryHeap<i32> = BinaryHeap::from(stones);
        while heap.len() > 1 {
            let val1 = heap.pop().unwrap();
            let val2 = heap.pop().unwrap();
            if val1 != val2 {
                heap.push(val1 - val2);
            }
        }
        heap.pop().unwrap_or(0)
    }
}
```

**Vergleich:** Der Heap wird jetzt per `BinaryHeap::from` in O(n) ohne Neuallokation aufgebaut statt mit n einzelnen `push`es. Bei Gleichstand wird keine 0 mehr zurückgeschoben; die 0 war zwar harmlos, kostete aber unnötige Heap-Operationen. Das Ende ist von `if let … else` über `match` und `unwrap_or_default` zu `unwrap_or(0)` geworden.

Die Alternative mit dem Counting-Array ist nur als Idee besprochen, nicht implementiert.

### Wo ich hing

- Wie ein Heap benutzt wird: die Vorstellung, Ergebnisse selbst in den Baum einhängen zu müssen. Die eigene Skizze hatte außerdem die 1 oben, bei einem Max-Heap gehört dort das größte Element hin.
- Komplexität pro Operation mit Gesamtkomplexität verwechselt (O(log n) statt O(n log n)).
- Die Alternative zuerst verworfen, weil die Suche nach dem nächsten belegten Index teuer wirkte, bis klar war, dass der Index nur in eine Richtung läuft.

### Rust-Learnings

- **`std::collections::BinaryHeap`** ist standardmäßig ein Max-Heap. `pop` liefert `Option<T>` mit dem größten Element.
- **`BinaryHeap::from(vec)`** baut den Heap in O(n) direkt aus einem `Vec`, ohne Neuallokation. Gefunden über die Trait-Implementierungen in der Doku.
- **`Option`-Methoden:** `unwrap_or(0)` bzw. `unwrap_or_default()` ersetzen das Muster `if let Some(x) … else { 0 }`. `unwrap_or(0)` ist expliziter, weil man den Default-Wert direkt sieht.
- **Typinferenz:** `0 as i32` ist überflüssig, der Rückgabetyp legt den Typ des Literals fest.
- **`unwrap()` in der Schleife** ist vertretbar, weil `heap.len() > 1` garantiert, dass beide `pop`s etwas liefern.
