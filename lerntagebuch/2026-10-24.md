# Lerntagebuch – 2026-10-24

## 83. Remove Duplicates from Sorted List (Easy)

- **Muster:** Verkettete Liste in-place umverlinken – ein Zeiger läuft mit, Duplikate werden durch Überspringen ausgehängt (bleibt stehen, solange der Nachfolger gleich ist)
- **Hinweisstufe benötigt:** 4 (Algorithmus komplett selbst inkl. „stehen bleiben bei mehreren Duplikaten“ und O(n)/O(1); für die Rust-Umsetzung Stufe 2 zu `&mut`/`as_mut()`/`take()` und am Ende Stufe 4 – Skelett mit Lücken – für den Borrow-Konflikt E0506)
- **Komplexität:** Zeit O(n), Speicher O(1)
- **Status:** kompiliert, Tests lokal grün, Einreichung offen
- **Wiederholen am:** 2026-10-27, dann 2026-10-31, dann 2026-11-24

### Aufgabe

Gegeben ist der `head` einer aufsteigend sortierten einfach verketteten Liste. Entferne alle Duplikate, sodass jeder Wert nur einmal vorkommt, und gib die (weiterhin sortierte) Liste zurück.

**Constraints:** 0–300 Knoten, `-100 <= Node.val <= 100`, Liste aufsteigend sortiert.

Beispiele: `[1,1,2]` → `[1,2]`; `[1,1,2,3,3]` → `[1,2,3]`. Eigene Testfälle: `[]`, `[5]`, `[1,1,1,2]`, `[7,7,7,7]`, `[-100,-3,0,100]`.

### Kernidee (eigene Worte)

> Man läuft über die Liste, indem man jeden nächsten Wert prüft. Sind sie gleich, wird die aktuelle Referenz auf den nächsten Wert verworfen, aber davor holt man sich sozusagen den übernächsten Wert und legt ihn als neue nächste Referenz ab. Sind die Werte unterschiedlich, gehen wir die Liste einen Index sozusagen weiter, bzw. eine Referenz weiter.

**Schärfung:** Verworfen wird nicht nur die Referenz, sondern der ganze Duplikat-Knoten: `now.next` *besitzt* seinen Nachfolger, und beim Überschreiben wird der alte Knoten automatisch gedroppt. Und wichtig: Nach dem Aushängen bleibt man stehen – erst bei unterschiedlichem Wert geht es weiter. Das funktioniert nur, weil die Liste sortiert ist und Duplikate deshalb direkt nebeneinander stehen.

### Weg zur Lösung

1. **Erste Idee:** Neue Liste ohne Duplikate bauen – selbst verworfen wegen O(n) Zusatzspeicher.
2. **Zweite Idee:** Ersten Knoten eines Werts direkt mit dem ersten Knoten des nächsten Werts verlinken.
3. **Handdurchlauf `[1,1,1,2]`:** Nach dem Aushängen *stehen bleiben*, weil noch ein weiteres Duplikat folgen kann; erst bei unterschiedlichem Wert weiterrücken.
4. **Komplexität:** Jeder Schritt hängt entweder einen Knoten aus oder rückt weiter → insgesamt höchstens n Schritte, O(n); kein Zusatzspeicher, O(1).
5. **Rust-Umsetzung:** `if let`-Richtung korrigiert → mit `&mut` statt Ownership durch die Liste wandern (`head.as_mut()`) → `take()` zum Herausnehmen des übernächsten Knotens → `else`-Zweig zum Weiterrücken selbst ergänzt → Borrow-Konflikt (E0506) gelöst, indem jede Leihe erst in der Zeile geholt wird, in der sie gebraucht wird.

### Meine Lösung

Erste Fassung (scheitert an E0506):

```rust
impl Solution {
    pub fn delete_duplicates(mut head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
        if let Some(mut now) = head.as_mut() {
            while let Some(next) = now.next.as_mut() {
                if now.val == next.val {
                    now.next = next.next.take();
                } else {
                    now = next;
                }
            }
        }
        return head;
    }
}
```

Endfassung (Tests grün):

```rust
impl Solution {
    pub fn delete_duplicates(mut head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
        if let Some(mut now) = head.as_mut() {
            while now.next.is_some() {
                if now.val == now.next.as_ref().unwrap().val {
                    now.next = now.next.as_mut().unwrap().next.take();
                } else {
                    now = now.next.as_mut().unwrap();
                }
            }
        }
        head
    }
}
```

Unterschied: In der ersten Fassung lebt die Leihe `next` über beide Zweige; in der Endfassung entsteht jede Leihe frisch in der Zeile, in der sie gebraucht wird.

Offene Idee (noch nicht umgesetzt): Die drei `unwrap()` sind dank `is_some()` sicher, aber es gibt Formulierungen mit `while let`, die ganz ohne `unwrap()` auskommen.

### Wo ich hing

- `if let now = Some(head)`: Muster und Wert vertauscht – hat `head` nochmal eingepackt statt auszupacken.
- `if let Some(now) = head` hat `head` verschoben, danach war `return head` nicht mehr möglich → Unterschied Besitzen vs. mit `&mut` durchlaufen.
- `now.next.as_mut() = …`: An einen temporären Wert kann man nicht zuweisen, nur an einen Ort (`now.next = …`).
- E0596: Parameter `head` war nicht `mut`.
- E0506 „cannot assign to `now.next` because it is borrowed“: Wegen `now = next` im `else`-Zweig muss die Leihe aus `while let` so lange leben wie `now` – auch im `if`-Zweig. Hier brauchte ich das Skelett (Stufe 4).

### Rust-Learnings

- `Box<T>`: besitzender Zeiger auf den Heap, gibt beim Drop frei; nötig für rekursive Typen, weil sonst die Größe unendlich wäre. `Option<Box<T>>` statt Null-Pointer, dank Nullpointer-Optimierung so groß wie ein Pointer.
- `if let MUSTER = WERT` – links das Muster, rechts der Wert.
- `Option::as_mut()` → `Option<&mut T>`, `Option::as_ref()` → `Option<&T>`, `Option::take()` nimmt den Wert heraus und lässt `None` zurück.
- Nur so viel Zugriff anfordern wie nötig: `as_ref()` zum Lesen, `as_mut()` nur wo geschrieben wird.
- Funktionsparameter sind wie alle Bindungen standardmäßig unveränderlich → `mut head`.
- Borrow-Checker-Grenze: Eine Leihe, die in einem Zweig in eine länger lebende Variable wandert, gilt für den Compiler auch im anderen Zweig als aktiv. Lösung: Leihen erst in jedem Zweig frisch holen.
- `now.next = now.next.as_mut().unwrap().next.take();` ist erlaubt: Die rechte Seite ist ausgewertet (und die Leihe beendet), bevor zugewiesen wird.
- Idiomatische Rückgabe: letzter Ausdruck ohne `return` und ohne Semikolon.
