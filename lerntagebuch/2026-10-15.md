# Lerntagebuch – 2026-10-15

## 373. Find K Pairs with Smallest Sums (Medium)

- **Muster:** Min-Heap / „k kleinste aus sortierten Listen“ (Frontier-Erkundung von `(0,0)` aus); Alternative: k-Wege-Merge mit Startpaaren `(i, 0)`
- **Hinweisstufe benötigt:** 2 (Werkzeug-Hinweis: zusätzliche Datenstruktur für „schon gesehen?“ in O(1) → `HashSet`; beim Robustheitsargument fürs `unwrap` ein Stufe-1-Hinweis mit der Kette ab `(0,0)`. Die Alternative ohne Set hat er in fremden Lösungen nachgelesen und danach selbst begründet.)
- **Komplexität:** Zeit O(k log k), Speicher O(k); Alternative: Zeit O(k log k), Heap mit höchstens min(n1, k) Elementen, kein Set
- **Status:** lokale Tests grün, Einreichung offen
- **Wiederholen am:** 2026-10-18, dann 2026-10-22, dann 2026-11-15

### Aufgabe

Gegeben sind zwei aufsteigend sortierte Arrays `nums1`, `nums2` und eine Zahl `k`. Ein Paar `(u, v)` besteht aus einem Element aus `nums1` und einem aus `nums2`. Zurückgegeben werden die `k` Paare mit den kleinsten Summen.

**Constraints:** `1 <= nums1.length, nums2.length <= 10^5`, `-10^9 <= nums1[i], nums2[i] <= 10^9`, beide sortiert, `1 <= k <= 10^4`, `k <= nums1.length * nums2.length`

Beispiele: `[1,7,11]`, `[2,4,6]`, `k = 3` → `[[1,2],[1,4],[1,6]]`; `[1,1,2]`, `[1,2,3]`, `k = 2` → `[[1,1],[1,1]]`; eigener Duplikat-Test `[1,2,3]`, `[1,2,3]`, `k = 6`

### Kernidee (eigene Worte)

> Die Kernidee ist es, einen Min-Heap zu haben und dort die Paare einzutragen. Damit man nicht alle Paare eintragen muss, fängt man damit an, für das gepoppte Element vom Heap seine Nachfolger zu bestimmen und wieder im Heap einzufügen. Das kann man dann so lange machen, bis man k voll hat.

**Schärfung:** Zwei Dinge fehlen im Satz. *Warum* reichen die Nachfolger? Weil beide Arrays sortiert sind, gilt `sum(i, j) <= sum(i+1, j)` und `sum(i, j) <= sum(i, j+1)`. Ein Paar kann also nie vor seinen Vorgängern drankommen. Außerdem hat `(i, j)` zwei Vorgänger. Ohne Duplikat-Schutz (Set oder Start mit allen `(i, 0)` und nur `j+1` als Nachfolger) landen Paare doppelt im Heap.

### Weg zur Lösung

1. **Eigener Start:** Heap mit kleinstem Element oben, Summe + Indizes speichern, nur die nötigen Paare erzeugen, weil die Arrays sortiert sind.
2. **Kleinstes Paar:** `(0,0)`, danach kommen nur `(0,1)` und `(1,0)` in Frage. `(0,2)` kann erst nach `(0,1)` kommen.
3. **Handsimulation** an Beispiel 1: zunächst uneinheitliche Regel (nach `(0,1)` nur `(0,2)` eingefügt). Mit fester Regel „`(i+1, j)` und `(i, j+1)`“ selbst entdeckt, dass `(1,1)` doppelt eingefügt wird.
4. **Duplikate verhindern:** erst „im Heap suchen“ (O(n)), dann ein 2D-Bool-Array (O(1), aber 10¹⁰ Einträge ≈ 10 GB, bei nur O(k) belegten). Mit dem Hinweis auf eine Collection, die nur die belegten Einträge speichert, kam er auf `HashSet<(usize, usize)>`.
5. **Komplexität:** Speicher O(k) sofort richtig. Bei der Zeit zuerst O(k), dann die Kosten von `push`/`pop` falsch geschätzt (O(k log k) bzw. O(k)). Über Knoten pro Ebene (1, 2, 4, …, 2¹⁰ ≈ 1000) kam er auf die Heap-Höhe log₂ n und damit auf O(k · 3 log k) = O(k log k).
6. **Indizes statt Werte** im Heap, weil man nach dem `pop` die Nachfolger bilden muss. Aus den Werten wären die Positionen nicht rekonstruierbar, bei Duplikaten sogar mehrdeutig.
7. **Alternative** (nachgelesen): alle `(i, 0)` für `i < min(n1, k)` vorab einfügen, danach nur `(i, j+1)`. Jedes Paar hat dann genau einen Vorgänger `(i, j-1)`, und das Set entfällt.

### Meine Lösung

Erste lauffähige Fassung (Tests grün, aber `set` wurde nur beschrieben, nie gelesen):

```rust
impl Solution {
    pub fn k_smallest_pairs(nums1: Vec<i32>, nums2: Vec<i32>, k: i32) -> Vec<Vec<i32>> {
        let mut set: HashSet<(usize, usize)> = HashSet::new();
        let mut heap: BinaryHeap<Reverse<(i32, usize, usize)>> = BinaryHeap::new();
        let mut ans: Vec<Vec<i32>> = Vec::with_capacity(k as usize);
        set.insert((0, 0));
        heap.push(Reverse((nums1[0] + nums2[0], 0, 0)));
        for _ in 0..k {
            let lowest = heap.pop().unwrap();
            let i = lowest.0.1;
            let j = lowest.0.2;
            ans.push(vec![nums1[i], nums2[j]]);
            if i + 1 < nums1.len() {
                set.insert((i + 1, j));
                heap.push(Reverse((nums1[i + 1] + nums2[j], i + 1, j)));
            }
            if j + 1 < nums2.len() {
                set.insert((i, j + 1));
                heap.push(Reverse((nums1[i] + nums2[j + 1], i, j + 1)));
            }
        }
        ans
    }
}
```

Endfassung nach dem Review:

```rust
impl Solution {
    pub fn k_smallest_pairs(nums1: Vec<i32>, nums2: Vec<i32>, k: i32) -> Vec<Vec<i32>> {
        let mut set: HashSet<(usize, usize)> = HashSet::new();
        let mut heap: BinaryHeap<Reverse<(i32, usize, usize)>> = BinaryHeap::new();
        let mut ans: Vec<Vec<i32>> = Vec::with_capacity(k as usize);
        set.insert((0, 0));
        heap.push(Reverse((nums1[0] + nums2[0], 0, 0)));
        for _ in 0..k {
            let Reverse((_, i, j)) = heap.pop().unwrap();
            ans.push(vec![nums1[i], nums2[j]]);
            if i + 1 < nums1.len() && set.insert((i + 1, j)) {
                heap.push(Reverse((nums1[i + 1] + nums2[j], i + 1, j)));
            }
            if j + 1 < nums2.len() && set.insert((i, j + 1)) {
                heap.push(Reverse((nums1[i] + nums2[j + 1], i, j + 1)));
            }
        }
        ans
    }
}
```

Vergleich: Die erste Fassung bestand die vorgegebenen Tests nur zufällig. Erst der Test `[1,2,3]`, `[1,2,3]`, `k = 6` deckt die doppelt ausgegebenen `(1,1)` auf. Die Endfassung prüft und fügt in einem Schritt über den Rückgabewert von `insert` ein und entpackt `Reverse` per Pattern.

Offene Ideen (in Worten): Alternative ohne Set selbst implementieren (Start mit `(i, 0)` für `i < min(n1, k)`, nur `j+1` als Nachfolger). Kommentar über dem `unwrap()`, warum der Heap nicht leer sein kann.

### Wo ich hing

- Regel für Nachfolger bei der Handsimulation zunächst nicht konsequent angewendet, dadurch die Duplikate übersehen.
- Duplikat-Schutz: Datenstruktur für „schon gesehen?“ ist mir nicht eingefallen (2D-Array → Speicherproblem → `HashSet` erst nach Hinweis).
- Heap-Kosten: `push`/`pop` nicht als O(log n) im Kopf. Den Zusammenhang Baumhöhe ↔ Logarithmus musste ich über das Zählen der Knoten pro Ebene neu herleiten.
- Begründung fürs `unwrap()`: erst „pro pop kommt mindestens eins dazu“ (falsch, Gegenbeispiel `[1,2]`, `[3]`). Das richtige Argument: Das erste noch nicht ausgegebene Paar auf der Kette ab `(0,0)` muss im Heap liegen.
- Set zwar befüllt, aber nie abgefragt. Die Tests waren trotzdem grün.

### Rust-Learnings

- `BinaryHeap` ist ein **Max-Heap**. Als Min-Heap über `std::cmp::Reverse`, und der Heap-Typ muss dann `BinaryHeap<Reverse<T>>` lauten (Fehler „expected `(i32, usize, usize)`, found `Reverse<…>`“).
- **Tupel vergleichen lexikographisch:** Summe als erstes Feld bestimmt die Ordnung, die Indizes dahinter entscheiden nur bei Gleichstand.
- `Reverse` ist ein **Tuple-Struct** mit einem Feld: Zugriff über `.0` (also `x.0.1`) oder eleganter per Pattern `let Reverse((_, i, j)) = …;`, wobei `_` Unbenutztes verwirft.
- `for n in 0..k` mit `k: i32` liefert `i32`. `Vec` lässt sich aber nur mit `usize` indizieren („cannot be indexed by `i32`“). Außerdem überdeckte der Schleifenname das äußere `i`.
- `Vec::with_capacity(k)` reserviert nur Speicher, die **Länge bleibt 0**. Daher der Panic „len is 0 but the index is 0“ bei `ans[n] = …`, die Lösung ist `push`.
- `HashSet::insert` gibt `bool` zurück (`true` = war neu). Damit ersetzt `set.insert(x)` das Muster `!contains` + `insert`. In Kombination mit `&&` und der Randprüfung davor sorgt die Kurzschlussauswertung dafür, dass keine ungültigen Paare im Set landen.
- `HashSet<(usize, usize)>` funktioniert direkt, weil Tupel `Hash`/`Eq` erben. `BTreeSet` ginge auch, kostet aber O(log n).
- Überlauf geprüft: ±10⁹ + ±10⁹ = ±2 · 10⁹ passt noch in `i32` (±2,147 · 10⁹).
