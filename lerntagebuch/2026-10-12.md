# Lerntagebuch – 2026-10-12

## 2073. Time Needed to Buy Tickets (Easy)

- **Muster:** Zählen statt Simulieren (Beitrag jedes Elements direkt berechnen)
- **Hinweisstufe benötigt:** 1 (Leitfrage: „Wie viele Tickets hat jede Person gekauft, wenn k fertig ist?“). Die Regel für Personen hinter k kam über das Gegenbeispiel `[3,1]` mit k=0. Beim Rust-Review gab es auf Nachfrage ein allgemeines Syntaxbeispiel zu Closures mit Block-Rumpf.
- **Komplexität:** Zeit O(n), zusätzlicher Speicher O(1)
- **Status:** eingereicht und bei LeetCode bestanden
- **Wiederholen am:** 2026-10-15, dann 2026-10-19, dann 2026-11-12

### Aufgabe

`n` Personen stehen in einer Schlange, Person `i` will `tickets[i]` Tickets kaufen. Ein Ticket kostet 1 Sekunde. Danach stellt sich die Person hinten an. Wer fertig ist, verlässt die Schlange. Gesucht ist die Zeit, bis die Person an der Startposition `k` fertig ist.

**Constraints:** `1 <= n <= 100`, `1 <= tickets[i] <= 100`, `0 <= k < n`

| tickets | k | Ausgabe |
|---|---|---|
| `[2,3,2]` | 2 | 6 |
| `[5,1,1,1]` | 0 | 8 |
| `[3,1]` (eigener Test) | 0 | 4 |
| `[2,3]` (eigener Test) | 0 | 3 |
| `[7]` (eigener Test) | 0 | 7 |

### Kernidee (eigene Worte)

> Die Kernidee ist es, über das Array zu laufen und den Minimalwert zwischen dem aktuell betrachteten Wert und dem Wert von tickets[k] zu nehmen, da entweder die Tickets schon alle gekauft sind, bevor k seine Tickets gekauft hat, oder k weniger Tickets hat und wir nur so lange schauen, bis k seine Tickets hat. Das sind dann gleich viele, wenn er vor k in der Schlange ist. Steht man hinter k in der Schlange, nimmt man den Mindestwert zwischen ticket und tickets[k] - 1, da in dem Fall die Personen hinter k nicht mehr betrachtet werden.

**Schärfung:** „Nicht mehr betrachtet“ meint genauer: In der **letzten Runde** von k sind die Personen hinter k noch nicht an der Reihe, wenn k fertig wird. In allen Runden davor kaufen sie normal mit.

### Weg zur Lösung

1. **Erster Gedanke:** Die Schlange simulieren. Das wäre bei den Constraints (≤ 10⁴ Schritte) völlig in Ordnung, aber es gab den Verdacht auf einen eleganteren Weg.
2. **Erkenntnis an Beispiel 1:** Beim Zählen der Tickets pro Person bis zum Ende von k kam heraus: Jede Person kauft höchstens `tickets[k]` Tickets, also `min(tickets[i], tickets[k])`.
3. **Vor/hinter k:** Wer hinter k steht, verliert die letzte Runde. Die erste Regel („hinter k immer −1“) widerlegte das Gegenbeispiel `[3,1]`. Richtig ist −1 nur, wenn die Person mindestens so viele Tickets will wie k.
4. **Vereinfachung:** Die beiden Fälle hinter k lassen sich zu `min(ticket, tickets[k] - 1)` zusammenfassen. Damit sind beide Zweige symmetrisch.

### Meine Lösung

Erste Fassung (Tests grün, aber fehlerhaft: verglich `ticket` mit dem **Index** `k` statt mit `tickets[k]`, und `==` statt `>=`):

```rust
impl Solution {
    pub fn time_required_to_buy(tickets: Vec<i32>, k: i32) -> i32 {
        let mut time: i32 = 0;
        for (idx, &ticket) in tickets.iter().enumerate() {
            if idx <= k as usize {
                time += i32::min(ticket, tickets[k as usize]);
            } else {
                if ticket == k {
                    time += ticket - 1;
                } else {
                    time += i32::min(ticket, tickets[k as usize])
                }
            }
        }
        time
    }
}
```

Korrigierte Schleifenfassung (Hilfsvariable, zusammengefasste Zweige):

```rust
impl Solution {
    pub fn time_required_to_buy(tickets: Vec<i32>, k: i32) -> i32 {
        let mut time: i32 = 0;
        let k_ticket: i32 = tickets[k as usize];
        for (idx, &ticket) in tickets.iter().enumerate() {
            if idx <= k as usize {
                time += i32::min(ticket, k_ticket);
            } else {
                time += i32::min(k_ticket - 1, ticket);
            }
        }
        time
    }
}
```

Finale Fassung (Iterator-Kette):

```rust
impl Solution {
    pub fn time_required_to_buy(tickets: Vec<i32>, k: i32) -> i32 {
        let k_ticket: i32 = tickets[k as usize];
        tickets
            .iter()
            .enumerate()
            .map(|(idx, &ticket)| {
                if idx <= k as usize {
                    return i32::min(ticket, k_ticket);
                } else {
                    return i32::min(k_ticket - 1, ticket);
                }
            })
            .sum()
    }
}
```

**Vergleich:** Beide korrekten Fassungen tun dasselbe. Die Iterator-Kette kommt ohne veränderliches `time` aus.

Offene Stil-Idee: `if/else` ohne `return` als Tail-Ausdruck der Closure schreiben.

### Wo ich hing

- Vergleich mit `k` statt mit `tickets[k]`. Die Beispieltests haben das nicht aufgedeckt, erst der Handdurchlauf mit `[2,3]`.
- `==` statt `>=`, außerdem `ticket - 1` statt `tickets[k] - 1` im Zweig hinter k.
- Iterator-Fassung: Mehrzeilige Logik in `map` war nicht mehr präsent. Dazu kamen ein überflüssiges `.collect()` und ein Semikolon nach `.sum()`.

### Rust-Learnings

- Closures können einen Block `{ ... }` als Rumpf haben. Der letzte Ausdruck ohne Semikolon ist der Rückgabewert.
- `sum()` ist direkt auf `Iterator` definiert. Ein `collect()` vorher ist unnötig, und ohne Typangabe meldet der Compiler E0282.
- Ein Semikolon nach dem letzten Ausdruck macht ihn zur Anweisung. Die Funktion gibt dann `()` zurück (E0308, „no tail expression“).
- Der Ergebnistyp von `sum()` ergibt sich aus dem Rückgabetyp der Funktion.
- Eine wiederholt genutzte Indexierung (`tickets[k as usize]`) gehört in eine lokale Variable.
- `k: i32` muss für Indexierung und den Vergleich mit `enumerate`-Indizes per `as usize` umgewandelt werden.
- Grüne Tests beweisen keine Korrektheit: gezielt Fälle testen, die jeden Zweig und jede Bedingung prüfen.
