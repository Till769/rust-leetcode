# Lerntagebuch – 2026-10-07

## 150. Evaluate Reverse Polish Notation (Medium)

- **Muster:** Stack
- **Hinweisstufe benötigt:** 0 (die Stack-Idee kam von dir, angestoßen durch die LeetCode-Kategorie)
- **Komplexität:** Zeit O(n), Speicher O(n)
- **Status:** kompiliert; Einreichung bei LeetCode noch nicht bestätigt
- **Wiederholen am:** 2026-10-10, dann 2026-10-14, dann 2026-11-07

### Aufgabe

Gegeben ist ein Array `tokens` aus Strings, das einen arithmetischen Ausdruck in umgekehrter polnischer Notation darstellt. Der Ausdruck soll ausgewertet und das Ergebnis als Ganzzahl zurückgegeben werden.

- Gültige Operatoren sind `+`, `-`, `*` und `/`.
- Jeder Operand ist eine Ganzzahl oder ein weiterer Ausdruck.
- Die Division zweier Ganzzahlen schneidet in Richtung null ab.
- Es gibt keine Division durch null, und die Eingabe ist immer ein gültiger Ausdruck.
- Ergebnis und alle Zwischenergebnisse passen in 32 Bit.

**Constraints:** `1 <= tokens.length <= 10^4`; jedes Token ist ein Operator oder eine Ganzzahl in `[-200, 200]`.

| Eingabe | Ausgabe |
|---|---|
| `["2","1","+","3","*"]` | 9 |
| `["4","13","5","/","+"]` | 6 |
| `["10","6","9","3","+","-11","*","/","*","17","+","5","+"]` | 22 |

### Kernidee (eigene Worte)

> Die Kernidee ist, den Stream von Tokens so zu verarbeiten, dass man immer mit den Top-Elementen des Stacks arbeitet. Nutzbar ist es durch die Art und Weise, wie die Tokens im Stream geordnet sind: erst die Zahlen, dann die Operatoren. So kann der Stack erst aufgebaut und dann pro Operator abgebaut werden.

**Schärfung:** Zahlen und Operatoren können sich abwechseln (Beispiel 1: `2 1 + 3 *`), der Stack wächst und schrumpft also mehrfach. Die tragende Eigenschaft ist: Jeder Operator steht direkt hinter seinen beiden fertigen Operanden, und die liegen deshalb immer oben auf dem Stack.

### Weg zur Lösung

1. **Erster Ansatz:** Im Array den ersten Operator suchen, auf die zwei Zahlen davor anwenden und die drei Tokens durch das Ergebnis ersetzen. Korrekt, aber jede Ersetzung verschiebt alle noch nicht gelesenen Elemente: O(n) pro Ersetzung, (n−1)/2 Ersetzungen, zusammen O(n²).
2. **Erkenntnis:** Verschoben wird genau der Teil, den man noch gar nicht angeschaut hat. Legt man das bereits Verarbeitete auf einen Stack, bleibt der Rest unangetastet, und `push`/`pop` kosten O(1).
3. **Operanden-Reihenfolge:** Der zuerst gepoppte Wert ist der rechte Operand, also `y / x` und `y - x`.
4. **Speicher im schlimmsten Fall:** alle Zahlen zuerst, dann alle Operatoren, z. B. `[1,1,1,1,1,1,1,1,+,+,+,+,+,+,+]`. Der Stack wächst auf (n+1)/2 Elemente.

### Meine Lösung

Eingereichte Fassung (ein `match` als Ausdruck, ein `push` am Ende):

```rust
impl Solution {
    pub fn eval_rpn(tokens: Vec<String>) -> i32 {
        let mut stack: Vec<i32> = Vec::new();
        for t in tokens {
            let o = match t.as_str() {
                "+" | "-" | "*" | "/" => {
                    let x = stack.pop().unwrap();
                    let y = stack.pop().unwrap();
                    match t.as_str() {
                        "+" => y + x,
                        "-" => y - x,
                        "*" => y * x,
                        "/" => y / x,
                        _ => unreachable!("unknown operator {t}"),
                    }
                },
                _ => t.parse::<i32>().unwrap(),
            };
            stack.push(o);
        }
        stack.pop().unwrap()
    }
}
```

Erste funktionierende Fassung (`if let` für die Unterscheidung Zahl/Operator):

```rust
impl Solution {
    pub fn eval_rpn(tokens: Vec<String>) -> i32 {
        let mut stack: Vec<i32> = Vec::new();
        for t in tokens {
            if let Ok(num) = t.parse::<i32>() {
                stack.push(num);
            } else {
                let x = stack.pop().unwrap();
                let y = stack.pop().unwrap();
                match t.as_str() {
                    "+" => stack.push(y + x),
                    "-" => stack.push(y - x),
                    "*" => stack.push(y * x),
                    "/" => stack.push(y / x),
                    &_ => todo!(),
                }
            }
        }
        stack.pop().unwrap()
    }
}
```

**Vergleich:** Die zweite Fassung nennt die vier Operatoren doppelt und braucht das innere `unreachable!` nur, weil der Compiler die äußere Filterung nicht kennt. Die `if let`-Fassung ist dadurch leichter zu lesen. Offene Idee: `if let` behalten und nur das "`match` als Ausdruck + ein `push`" übernehmen, dazu `unreachable!` statt `todo!`.

### Wo ich hing

- `let x,y: i32;` gibt es in Rust nicht.
- `pop()` liefert `Option<i32>`, nicht `i32` (fünf der neun Compilermeldungen).
- `match` auf einem `String` mit `&str`-Mustern (die anderen vier Meldungen).
- Wie man das Token als Operator in der Rechnung verwendet.

### Rust-Learnings

- `parse::<i32>()` liefert `Result<i32, ParseIntError>`. Umgang damit: `match`, `if let ... else`, `unwrap_or`, `?`; `unwrap()`/`expect()` nur, wenn der Fehlerfall laut Vertrag ausgeschlossen ist.
- `Vec::pop()` liefert `Option<T>`, weil der Vektor leer sein kann.
- `String::as_str()` gibt die `&str`-Sicht, auf der man mit String-Literalen matchen kann.
- Variablen müssen `mut` sein, wenn man sie verändert (`let mut stack`).
- `match` muss alle Fälle abdecken; als Auffang-Muster reicht `_`.
- `todo!()` heißt "fehlt noch", `unreachable!()` heißt "kann laut Vertrag nicht passieren", `panic!()` ist der allgemeine Abbruch.
- `match` ist ein Ausdruck und liefert einen Wert; Zweige können Blöcke `{ ... }` sein, mehrere Muster verbindet `|`.
- Deklaration mehrerer Variablen: zwei `let` oder ein Tupel-Muster `let (x, y) = ...;`. Üblich ist, erst dort zu deklarieren, wo der Wert entsteht.
- Strings lassen sich nicht als Operatoren "ausführen"; die Abbildung Token → Operation macht ein `match`.

## 636. Exclusive Time of Functions (Medium)

- **Muster:** Stack (Call-Stack-Simulation)
- **Hinweisstufe benötigt:** 0–1 (Stack, Ergebnis-Array und die Abzugsidee kamen von dir; dass der Abzug beim leeren Stack entfällt, weil es dann keinen Aufrufer gibt, habe ich mit ausformuliert. Die Alternative mit `prev`-Zeitstempel habe ich am Ende verraten.)
- **Komplexität:** Zeit O(n + L), Speicher O(n + L) mit L = Anzahl der Logs; der Stack wird höchstens L/2 tief
- **Status:** eingereicht und akzeptiert
- **Wiederholen am:** 2026-10-10, dann 2026-10-14, dann 2026-11-07 (bei der Wiederholung die `prev`-Variante ohne Abzug versuchen)

### Aufgabe

Auf einer Single-Thread-CPU laufen `n` Funktionen mit IDs `0..n-1`. Jeder Start und jedes Ende eines Aufrufs erzeugt einen Log-Eintrag im Format `"{id}:{start|end}:{timestamp}"`. `start:3` heißt: beginnt am Anfang von Zeiteinheit 3; `end:2` heißt: endet am Ende von Zeiteinheit 2. Funktionen können mehrfach und rekursiv aufgerufen werden. Gesucht ist pro Funktion die exklusive Zeit, also die Summe ihrer Laufzeiten ohne die Zeit, in der von ihr aufgerufene Funktionen liefen.

**Constraints:** `1 <= n <= 100`; `2 <= logs.length <= 500`; `0 <= timestamp <= 10^9`; keine zwei Starts und keine zwei Enden zum selben Zeitstempel; zu jedem `start` gibt es ein `end`.

| n | logs | Ausgabe |
|---|---|---|
| 2 | `["0:start:0","1:start:2","1:end:5","0:end:6"]` | `[3,4]` |
| 1 | `["0:start:0","0:start:2","0:end:5","0:start:6","0:end:6","0:end:7"]` | `[8]` |
| 2 | `["0:start:0","0:start:2","0:end:5","1:start:6","1:end:6","0:end:7"]` | `[7,1]` |
| 2 | `["0:start:0","0:end:0","1:start:1","1:end:1"]` (eigener Test: zwei Top-Level-Aufrufe) | `[1,1]` |

### Kernidee (eigene Worte)

> Die Kernidee ist, über den Log zu laufen und sich pro Eintrag einmal die PID und die Zeit zu merken. Wurde der Prozess gestartet, werden diese Werte auf den Stack gepusht. Wurde der Prozess beendet, berechnen wir die Zeit zwischen dem obersten Stack-Wert und dem Wert aus dem Prozess-beenden-Log. Der Wert wird vom Stack entfernt. Zusätzlich müssen wir diese Zeit vom Parent-Prozess subtrahieren. Das machen wir so lange, bis der Log abgearbeitet ist.

**Schärfung:** Das ist der Ablauf, das "Warum" fehlt noch: `end − start + 1` ist die *inklusive* Dauer eines Aufrufs, also samt aller Kinder. Der Abzug beim Parent funktioniert, weil dessen eigene inklusive Dauer später die Kindzeit wieder mitzählt; beides hebt sich auf. Zwei Details gehören dazu: das `+1` (ein `end` gilt bis zum Ende der Zeiteinheit) und dass der Abzug nur passiert, wenn es einen Parent gibt, der Stack nach dem Pop also nicht leer ist.

### Weg zur Lösung

1. **Erster Ansatz:** Bei `start` pushen, bei `end` poppen und `end − start + 1` auf `ans[id]` addieren.
2. **Warum das nicht reichte:** Von Hand an Beispiel 1 durchgespielt, ergibt Funktion 0 den Wert 6 − 0 + 1 = 7 statt 3, weil die 4 Einheiten von Funktion 1 mitgezählt werden.
3. **Entscheidende Erkenntnis:** Nach dem Pop liegt der unterbrochene Aufrufer oben auf dem Stack, und man kennt in diesem Moment genau die Dauer der Unterbrechung. Sie wird sofort als negativer Wert bei `ans[aufrufer]` verbucht; `ans` darf zwischenzeitlich negativ sein.
4. **Rekursion (Beispiel 2):** Zunächst nach drei von sechs Einträgen abgebrochen und geschlossen, es komme immer 0 heraus. Zu Ende gespielt: Beim letzten `end` ist der Stack leer, es gibt keinen Aufrufer, also keinen Abzug, und es bleiben 8.
5. **Komplexität:** Erst O(n) geschätzt; `n` ist aber die Zahl der Funktionen, die Schleife läuft über die L Logs.
6. **Alternative (nicht implementiert):** Die Zeit zwischen zwei aufeinanderfolgenden Logs gehört immer der Funktion oben auf dem Stack. Mit einem `prev`-Zeitstempel und einem Stack nur aus IDs kommt man ohne Abzug aus. Gleiche Komplexität, andere Denkweise; heikel ist das `+1` beim `end`.

### Meine Lösung

Erste Fassung, kompilierte nicht (E0597, `&str` auf dem Stack überleben `l`); zusätzlich fehlte das `+1`, und `None => return ans` beendete die Funktion zu früh:

```rust
impl Solution {
    pub fn exclusive_time(n: i32, logs: Vec<String>) -> Vec<i32> {
        let mut ans: Vec<i32> = vec![0; n as usize];
        let mut stack: Vec<Vec<&str>> = Vec::new();
        for l in logs {
            let val: Vec<&str> = l.split(':').collect();
            match val[1] {
                "start" => stack.push(val),
                "end" => {
                    let pop = stack.pop().unwrap();
                    let time = val[2].parse::<i32>().unwrap() - pop[2].parse::<i32>().unwrap();
                    ans[val[0].parse::<usize>().unwrap()] += time;
                    match stack.last() {
                        Some(last) => ans[last[0].parse::<usize>().unwrap()] -= time,
                        None => return ans,
                    }
                },
                _ => unreachable!(),
            }
        }
        ans
    }
}
```

Eingereichte Fassung (geparste Zahlen im Tupel statt `&str`, Destructuring, `if let`):

```rust
impl Solution {
    pub fn exclusive_time(n: i32, logs: Vec<String>) -> Vec<i32> {
        let mut ans: Vec<i32> = vec![0; n as usize];
        let mut stack: Vec<(usize, usize)> = Vec::new();
        for l in logs {
            let val: Vec<&str> = l.split(':').collect();
            let (pid, end_time) = (val[0].parse::<usize>().unwrap(), val[2].parse::<usize>().unwrap());
            match val[1] {
                "start" => stack.push((pid, end_time)),
                "end" => {
                    let (_, start_time) = stack.pop().unwrap();
                    let time = (end_time - start_time + 1) as i32;
                    ans[pid] += time;
                    if let Some((ppid ,_)) = stack.last() {
                        ans[*ppid] -= time;
                    }
                },
                _ => unreachable!(),
            }
        }
        ans
    }
}
```

Vergleich: Die Zwischenfassungen nutzten erst `Vec<i32>` mit zwei Elementen pro Log (eine Heap-Allokation je Eintrag, `pop[1]` ohne Bedeutung), dann `(i32, i32)` mit `.0`/`.1` und `as usize`-Casts. Die Endfassung parst die ID direkt als `usize` und gibt den Tupel-Teilen Namen.

Offene Verbesserungsideen:

- `end_time` wird auch im `"start"`-Zweig gepusht und ist dort eine Startzeit; ein neutraler Name wie "Zeitstempel" wäre für beide Fälle richtig.
- `l` und `val` könnten sprechender heißen.
- Der Zwischen-`Vec<&str>` aus `split(':').collect()` ist eine Allokation pro Log, die sich vermeiden ließe.

### Wo ich hing

- Dass `end − start + 1` die Zeit der aufgerufenen Funktionen mitzählt, fiel erst beim Durchspielen von Beispiel 1 auf.
- "Wie merke ich mir die Unterbrechungszeit elegant?" Die Lösung war, sie gar nicht zu merken, sondern sofort beim Aufrufer zu verbuchen.
- Beispiel 2 zu früh abgebrochen und daraus ein falsches Endergebnis abgeleitet.
- `None => return ans` lief bei den drei LeetCode-Beispielen durch, weil sie nur einen Top-Level-Aufruf haben; erst der eigene Testfall mit zwei Top-Level-Aufrufen deckt das auf.
- Borrow-Fehler E0597: erste Reaktion war "`l` klonen", was nicht hilft, weil auch der Klon am Schleifenende gedroppt würde.
- n (Funktionen) und L (Logs) in der Komplexitätsanalyse verwechselt.

### Rust-Learnings

- **E0597 "does not live long enough":** `split` liefert `&str`, die in den Speicher des Ausgangs-Strings zeigen. `for l in logs` *bewegt* jeden `String` in `l`; `l` ist Eigentümer und wird am Ende jedes Durchlaufs gedroppt. Ein Stack, der die Schleife überlebt, darf deshalb nichts von `l` Geborgtes enthalten. Ausweg: eigenständige, geparste Werte ablegen.
- **Compilermeldungen von unten nach oben lesen:** wo wird gedroppt, wo wird später benutzt, wo entsteht die Leihgabe.
- **Tupel statt `Vec`** für eine feste Anzahl von Werten mit unterschiedlicher Bedeutung: keine Heap-Allokation.
- **Destructuring:** Links vom `let` steht ein Pattern, z. B. `let (_, start_time) = stack.pop().unwrap();`. Das geht auch in `if let Some((ppid, _)) = stack.last()`; weil `last()` eine Referenz liefert, ist `ppid` dort ein `&usize` und muss mit `*ppid` dereferenziert werden.
- **`if let`** statt `match`, wenn nur der `Some`-Fall interessiert.
- **Literale als Index** brauchen kein `as usize`; und Werte gleich in dem Typ parsen, in dem man sie braucht (`parse::<usize>()`), spart Casts.
- **`usize`-Subtraktion** ist hier sicher, weil `end_time >= start_time` garantiert ist; allgemein würde ein Unterlauf paniken.
