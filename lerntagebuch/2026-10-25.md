# Lerntagebuch – 2026-10-25

## 328. Odd Even Linked List (Medium)

- **Muster:** Verkettete Liste in zwei Ketten aufteilen und am Ende verbinden. Jede Kette hat einen Kopf und einen „Zeiger auf die nächste freie Stelle“ (Tail-Pointer).
- **Hinweisstufe benötigt:** 4. Den Algorithmus (zwei Ketten, je Ende merken, Anfang der geraden Kette fürs Verbinden) habe ich mit sokratischen Fragen selbst gefunden (Stufe 0–1). Für die Rust-Umsetzung brauchte ich Stufe 2 (Muster „Knoten vorne abnehmen“ mit `take()`) und Stufe 4 (Skelett mit `&mut Option<Box<ListNode>>` als Ende-Zeiger).
- **Komplexität:** Zeit O(n), Speicher O(1)
- **Status:** kompiliert, Tests lokal grün, Einreichung offen
- **Wiederholen am:** 2026-10-28, dann 2026-11-01, dann 2026-11-25

### Aufgabe

Gegeben ist der `head` einer einfach verketteten Liste. Gruppiere alle Knoten mit ungeradem **Index** (1., 3., 5. …) zuerst und dahinter alle mit geradem Index. Die relative Reihenfolge innerhalb beider Gruppen bleibt erhalten. Gefordert sind Zeit O(n) und Speicher O(1).

**Constraints:** 0–10^4 Knoten, `-10^6 <= Node.val <= 10^6`.

Beispiele: `[1,2,3,4,5]` → `[1,3,5,2,4]`; `[2,1,3,5,6,4,7]` → `[2,3,6,7,1,5,4]`. Eigene Testfälle: `[]`, `[1]`, `[1,2]`, `[1,2,3,4,5,6]`, `[-1,-2,-3]`.

### Kernidee (eigene Worte)

> Über die Liste laufen und je nach Index schauen, ob gerade oder ungerade (läuft über bool), und den Knoten an die jeweilige Kette hängen, die man durch das neue Verlinken konstruiert. Am Ende wird die gerade Liste an die ungerade Liste angehängt.

### Weg zur Lösung

1. **Erste Idee:** In-place den jeweils nächsten ungeraden Knoten suchen und hinter den letzten ungeraden vorziehen. Das wäre korrekt und O(n)/O(1), fühlte sich aber umständlich an, weil man viele Variablen braucht.
2. **Perspektivwechsel:** Jeden Knoten nur einmal anfassen und sofort an seinen Zielort legen. Es gibt nur zwei Zielorte: die ungerade und die gerade Kette. Für jede Kette merkt man sich das Ende.
3. **Verbinden:** Am Schluss braucht man das Ende der ungeraden Kette und den Anfang der geraden Kette.
4. **O(1)-Speicher:** Die Ketten bestehen aus den vorhandenen Knoten. Man braucht nur eine feste Zahl an Zeigern, unabhängig von n.
5. **Stolperstein:** Zuerst habe ich nach `val % 2` sortiert statt nach der Position. Beispiel 2 zeigt, dass es um den Index geht, deshalb wird abwechselnd mit einem `bool` verteilt.
6. **Rust-Umsetzung:** Die Eingabe wie einen Stapel abarbeiten (`while let Some(mut node) = rest { rest = node.next.take(); … }`). Das Ende jeder Kette ist ein `&mut Option<Box<ListNode>>`, der auf die nächste freie Stelle zeigt. Er startet bei `&mut odd_head`, deshalb gibt es keinen Sonderfall für die leere Kette.

### Meine Lösung

```rust
impl Solution {
    pub fn odd_even_list(head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
        let mut rest = head;
        let mut odd_head: Option<Box<ListNode>> = None;
        let mut odd_end: &mut Option<Box<ListNode>> = &mut odd_head;
        let mut even_head: Option<Box<ListNode>> = None;
        let mut even_end: &mut Option<Box<ListNode>> = &mut even_head;
        let mut odd = true;
        while let Some(mut node) = rest {
            rest = node.next.take();
            if odd {
                *odd_end = Some(node);
                odd_end = &mut odd_end.as_mut().unwrap().next;
            } else {
                *even_end = Some(node);
                even_end = &mut even_end.as_mut().unwrap().next;
            }
            odd = !odd
        }
        *odd_end = even_head;
        odd_head
    }
}
```

Diskutierte Alternative (nicht umgesetzt): `std::mem::swap` auf zwei Enden (`current_end`/`other_end`) statt `if`/`bool`. Die Schleife wird kürzer, aber am Ende muss man doch wieder wissen, ob die Länge gerade oder ungerade war, um das ungerade Ende zu finden. Mein Urteil: Die `if`-Variante ist klarer.

### Wo ich hing

- Nach dem Knotenwert (`val % 2`) statt nach der Position unterschieden.
- Ohne Rust-Muster keine Idee, wie man mit zwei Ketten und deren Enden umgeht. Das Abnehmen der Knoten mit `take()` hat geholfen.
- `even_end: Option<Box<ListNode>>`: Das Ende als *besitzender* Typ geht nicht, weil der Knoten schon der Kette gehört.
- E0597/E0505: `odd_end = &node` leiht sich die lokale Variable, die direkt danach nach `odd_head` verschoben wird. Die Referenz muss auf den Knoten an seinem neuen Platz zeigen.
- E0594: `&` statt `&mut`, damit kann man nicht schreiben. E0381: Ende nicht initialisiert, wegen des Sonderfalls für die leere Kette.
- E0308: `&ListNode` vs. `&Option<Box<ListNode>>`. Das Ende muss auf die *Stelle* (`Option`) zeigen, nicht auf den Knoten. Hier brauchte ich das Skelett (Stufe 4).
- E0382: `head` nach dem Verschieben in `rest` zurückgegeben.
- Beim Verbinden `odd_end = &mut even_head` statt `*odd_end = even_head` geschrieben. Die Warnung „value assigned is never read“ hat es verraten.

### Rust-Learnings

- Muster „Liste abarbeiten“: `while let Some(mut node) = rest { rest = node.next.take(); … }`. Danach besitzt man jeden Knoten einzeln.
- Tail-Pointer in Rust: `&mut Option<Box<ListNode>>` zeigt auf die nächste freie Stelle (ein `None`). Anhängen geht so: `*end = Some(node);` und danach `end = &mut end.as_mut().unwrap().next;`. Startet man bei `&mut head`, entfällt der Sonderfall für die leere Liste.
- `x = …` ändert die Referenz selbst (wohin sie zeigt), `*x = …` schreibt an die Stelle, auf die sie zeigt.
- Eine Referenz auf eine lokale Variable wird ungültig, sobald der Wert verschoben wird (E0505/E0597).
- `std::mem` enthält `take`, `replace` und `swap`, die nützlich für Ownership-Tricks sind. `swap` tauscht die Inhalte zweier `&mut`-Stellen.
- Compiler-Warnungen wie „value assigned … is never read“ zeigen oft echte Logikfehler.
