# Lerntagebuch – 2026-10-19

## 482. License Key Formatting (Easy)

- **Muster:** String-Bereinigung per Iterator-Kette, dann ein Durchlauf mit Modulo-Regel zum Gruppieren
- **Hinweisstufe benötigt:** 0–1 (überwiegend Gegenfragen und Gegenbeispiele; beim `concat`-Fehler der Fingerzeig „diese Umwandlung hast du in den ersten Zeilen schon gemacht“, bei der Alternative die Frage, welche Gruppen immer voll sind)
- **Komplexität:** Zeit O(n), Speicher O(n)
- **Status:** eingereicht und bestanden, lokale Tests grün (6 Tests)
- **Wiederholen am:** 2026-10-22, dann 2026-10-26, dann 2026-11-19

### Aufgabe

Ein Lizenzschlüssel `s` besteht aus alphanumerischen Zeichen und Bindestrichen. Er soll so umformatiert werden, dass jede Gruppe genau `k` Zeichen hat. Nur die erste Gruppe darf kürzer sein, muss aber mindestens ein Zeichen haben. Zwischen den Gruppen steht ein Bindestrich, alle Kleinbuchstaben werden groß.

**Constraints:** `1 <= s.length <= 10^5`, `s` enthält englische Buchstaben, Ziffern und `'-'`; `1 <= k <= 10^4`.

Beispiele: `"5F3Z-2e-9-w"`, k = 4 → `"5F3Z-2E9W"`; `"2-5g-3-J"`, k = 2 → `"2-5G-3J"`. Weitere Testfälle: `"---"` → `""`, `"a-b-c"`/1 → `"A-B-C"`, `"-ab-cd-"`/2 → `"AB-CD"`, `"a-b"`/10 → `"AB"`.

### Kernidee (eigene Worte)

> Man formatiert erst den String, dass er keine Bindestriche und nur noch Großbuchstaben hat, über eine Funktionskette und geht dann darüber, um an den richtigen Stellen den Bindestrich wieder einzufügen. Die richtige Stelle ist dort, wo i % k == n % k ist.

**Schärfung:** `n` ist die Länge **nach** dem Entfernen der Bindestriche (genau daran hing der letzte Fehler), und die Regel gilt nur für `i > 0`. Sonst entsteht bei `n % k == 0` ein führender Bindestrich.

### Weg zur Lösung

1. **Zerlegung:** Bindestriche entfernen, Großschreibung, neu gruppieren. Die ersten beiden Schritte als Iterator-Kette, der dritte war offen.
2. **Länge der ersten Gruppe:** `n % k`, bzw. `k`, falls der Rest 0 ist.
3. **Erste Regel `i % k == 0`:** Am Beispiel `"25G3J"`, k = 2 von Hand durchgespielt. Ergebnis falsch, weil der Versatz der ersten Gruppe fehlt. Korrektur: `i % k == n % k`.
4. **Randfälle:** Bei Beispiel 1 (Rest 0) würde bei `i = 0` ein Bindestrich gesetzt, daher `i > 0`. Damit verschwindet der Sonderfall „Rest 0“ von selbst. Bei `"---"` läuft die Schleife gar nicht.
5. **Code:** Nacheinander behoben: `concat` auf `Vec<char>`, `filter` mit `==` statt `!=` (Ausgabe bestand nur aus Bindestrichen), `map` auf `s` statt `x`, und `rest` aus `s.len()` statt aus der bereinigten Länge.
6. **Review:** Zwei Ketten zu einer zusammengefasst, `String` statt `Vec<char>` als Puffer, `k` einmalig per Shadowing nach `usize` umgewandelt.
7. **Alternative:** Von hinten arbeiten. Dort sind alle Gruppen voll, und `rest` entfällt. Der Preis ist ein Umdrehen am Ende oder Einfügen vorne.

### Meine Lösung

Erste grüne Fassung:

```rust
impl Solution {
    pub fn license_key_formatting(s: String, k: i32) -> String {
        let s1: String = s.chars().filter(|&x| x != '-').collect();
        let s2: String = s1.chars().map(|x| x.to_ascii_uppercase()).collect();
        let mut ans: Vec<char> = Vec::new();

        let rest = s2.len() as i32 % k;

        for (i, x) in s2.char_indices() {
            if i as i32 % k == rest && i > 0 {
                ans.push('-');
            }
            ans.push(x);
        }
        ans.iter().collect()
    }
}
```

Endfassung nach Review:

```rust
impl Solution {
    pub fn license_key_formatting(s: String, k: i32) -> String {
        let string2: String = s
            .chars()
            .filter(|&x| x != '-')
            .map(|x| x.to_ascii_uppercase())
            .collect();
        let mut ans: String = String::new();
        let k = k as usize;

        let rest = string2.len() % k;

        for (i, x) in string2.char_indices() {
            if i % k == rest && i > 0 {
                ans.push('-');
            }
            ans.push(x);
        }
        ans
    }
}
```

Vergleich: Beide Fassungen brauchen O(n) Zeit und O(n) Speicher. Die Endfassung spart eine Zwischenkopie (`s1`), den Umweg über `Vec<char>` und alle Casts in der Schleife.

Offene Ideen: `String::with_capacity` für `ans` (Endlänge ist bekannt: n + Anzahl Bindestriche); `.chars().enumerate()` statt `char_indices()`, weil das die Absicht klarer ausdrückt; Rückwärts-Variante als Übung.

### Wo ich hing

- Erste Bindestrich-Regel `i % k == 0` ohne den Versatz der ersten Gruppe.
- Speicherkomplexität anfangs als O(1) geschätzt, obwohl neue Strings entstehen.
- Tippfehler in der Kette: `filter(|&x| x == '-')` behielt nur die Bindestriche, `map(|x| s.to_ascii_uppercase())` griff auf `s` statt auf `x` zu.
- `rest` aus `s.len()` (mit Bindestrichen) statt aus der bereinigten Länge berechnet. Vermutet wurde zuerst ein Problem beim Rest 0.
- Beim Umstellen auf `usize` die von LeetCode vorgegebene Signatur geändert.

### Rust-Learnings

- `[T]::concat` verbindet Slices bzw. Strings, nicht einzelne `char`s. Aus `char`s wird ein `String` per `collect()`.
- `filter` und `map` lassen sich direkt hintereinanderketten; ein `collect()` dazwischen kostet nur eine Kopie.
- `String::push(char)` hängt direkt an, ein `Vec<char>` als Puffer ist unnötig.
- `char_indices()` liefert Byte-Offsets, `len()` zählt Bytes. Das geht bei ASCII gut, bei anderem UTF-8 nicht. `.chars().enumerate()` zählt Zeichen.
- `usize` ist der natürliche Typ für Längen und Indizes. Einmal umwandeln per Shadowing (`let k = k as usize;`), die Signatur bleibt dabei unverändert.
- `as usize` auf einem negativen `i32` liefert eine riesige Zahl. Hier ist es sicher wegen `k >= 1`.
- Mehrere O(n)-Kopien bleiben O(n). Speicher-O(1) heißt: keine von n abhängige Allokation.
