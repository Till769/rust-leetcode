# Lerntagebuch – 2026-10-13

## 232. Implement Queue using Stacks (Easy)

- **Muster:** Zwei Stacks als Queue (Input-/Output-Stack, faules Umkippen), amortisierte Analyse
- **Hinweisstufe benötigt:** 1 (Handdurchlauf mit `push(1..3)`, umkippen, dann `push(4)` und der Leitfrage, ob die 4 wirklich in B landen muss. Für die amortisierte Begründung kam der Tipp, ein einzelnes Element von `push` bis `pop` zu verfolgen.) Zusätzlich gab es ein allgemeines Syntaxbeispiel zum Struct-Literal in `new` und Namensvorschläge für die Hilfsmethode.
- **Komplexität:** Zeit amortisiert O(1) pro Operation (ein einzelnes `pop`/`peek` im Worst Case O(n)), Speicher O(n)
- **Status:** eingereicht und bei LeetCode bestanden
- **Wiederholen am:** 2026-10-16, dann 2026-10-20, dann 2026-11-13

### Aufgabe

Eine FIFO-Queue soll nur mit zwei Stacks umgesetzt werden, mit den Operationen `push(x)`, `pop()`, `peek()` und `empty()`. Erlaubt sind nur Stack-Operationen: push auf den Top, peek/pop vom Top, size und is empty.

**Constraints:** `1 <= x <= 9`, höchstens 100 Aufrufe, `pop` und `peek` werden nur auf einer nicht leeren Queue aufgerufen.
**Follow-up:** Jede Operation soll amortisiert O(1) kosten.

Beispiel: `push(1), push(2), peek() → 1, pop() → 1, empty() → false`

### Kernidee (eigene Worte)

> Man verwendet zwei Stacks und wenn man Operationen am Anfang der Queue machen will, wird der Input-Stack einmal umgekippt auf den Output-Stack, auf den dann mit normalen Stack-Operationen die Queue-Operationen pop und peek durchgeführt werden können, da sich die Reihenfolge beim Umkippen ändert.

**Schärfung:** Entscheidend ist, *wann* umgekippt wird: **nur, wenn der Output-Stack leer ist**. Liegt dort noch etwas, sind diese Elemente älter als alles im Input-Stack. Ein Umkippen in diesem Moment würde neuere Elemente obenauf legen und die FIFO-Reihenfolge zerstören (`[3,2,1]` + `[4,5]` → `[3,2,1,5,4]`). Genau diese Regel macht auch das amortisierte O(1) möglich, denn jedes Element wird höchstens einmal umgekippt.

### Weg zur Lösung

1. **Ausgangsbeobachtung:** `push` und `empty` sind mit einem Stack trivial. Für `pop` und `peek` muss man aber an das unterste Element, deshalb braucht man zwei Stacks. Die Sorge war, dass der umgekehrte Stack dann für `push` dasselbe Problem hat.
2. **Handdurchlauf:** Nach `push(1..3)` und einmal Umkippen liegt B als `[3,2,1]` vor, mit 1 oben. Ein anschließendes `push(4)` kann einfach auf A, B muss dafür nicht angefasst werden.
3. **Gegenbeispiel selbst gefunden:** Würde man A wieder auf ein nicht leeres B kippen, entstünde `[3,2,1,5,4]`, und das ist die falsche Reihenfolge. Daraus folgte die Regel: `push` → A, `pop`/`peek` → B, umkippen nur bei leerem B, `empty` prüft beide.
4. **Amortisierung:** Jedes Element durchläuft höchstens 4 Stack-Operationen (push A, pop A, push B, pop B). Damit kosten n Operationen insgesamt O(n).

### Meine Lösung

Erste Fassung (Tests grün):

```rust
pub struct MyQueue {
    stack_a: Vec<i32>,
    stack_b: Vec<i32>,
}

impl MyQueue {
    pub fn new() -> Self {
        Self {
            stack_a: Vec::new(),
            stack_b: Vec::new(),
        }
    }

    pub fn push(&mut self, x: i32) {
        self.stack_a.push(x);
    }

    pub fn pop(&mut self) -> i32 {
        if self.b_is_empty() {
            self.umkippen();
        }
        self.stack_b.pop().unwrap()
    }

    pub fn peek(&mut self) -> i32 {
        if self.b_is_empty() {
            self.umkippen();
        }
        *self.stack_b.last().unwrap()
    }

    pub fn empty(&self) -> bool {
        self.stack_a.is_empty() && self.stack_b.is_empty()
    }

    fn b_is_empty(&self) -> bool {
        self.stack_b.is_empty()
    }

    fn umkippen(&mut self) {
        for _ in 0..self.stack_a.len() {
            self.stack_b.push(self.stack_a.pop().unwrap());
        }
    }
}
```

Endfassung nach dem Review (eingereicht, bestanden):

```rust
impl MyQueue {
    pub fn new() -> Self {
        Self {
            input: Vec::new(),
            output: Vec::new(),
        }
    }

    pub fn push(&mut self, x: i32) {
        self.input.push(x);
    }

    pub fn pop(&mut self) -> i32 {
        self.ensure_front();
        self.output.pop().unwrap()
    }

    pub fn peek(&mut self) -> i32 {
        self.ensure_front();
        *self.output.last().unwrap()
    }

    pub fn empty(&self) -> bool {
        self.input.is_empty() && self.output.is_empty()
    }

    fn ensure_front(&mut self) {
        if self.output.is_empty() {
            while let Some(value) = self.input.pop() {
                self.output.push(value);
            }
        }
    }
}
```

**Vergleich:** Die Logik ist gleich geblieben. Die Schleife mit `0..len()` und `unwrap()` wurde zu `while let`. Die doppelte Prüfung in `pop`/`peek` steht jetzt nur noch in `ensure_front`, sodass niemand die Kernregel vergessen kann. Außerdem beschreiben die Namen die Rolle (`input`/`output`) bzw. die Garantie (`ensure_front`) statt der Mechanik.

### Wo ich hing

- Anfangs die Annahme, dass der zweite Stack beim Umdrehen „dasselbe Problem“ bekommt. Das hat sich erst im Handdurchlauf aufgelöst: Man kippt nicht hin und her, sondern nur in eine Richtung und nur bei leerem Output.
- Die Syntax für das Erzeugen einer Struct in `new` musste nachgeschlagen werden.
- Die Namensgebung für die Hilfsmethode, nachdem die Bedingung hineingewandert war.

### Rust-Learnings

- **`Vec` als Stack:** `push`, `pop` (liefert `Option<T>`), `last` (liefert `Option<&T>`, daher `*` zum Dereferenzieren bei `i32`) und `is_empty`.
- **`&self` vs. `&mut self`:** Auch `peek` braucht `&mut self`, weil es eventuell umkippt. Für `empty` reicht `&self`.
- **Struct-Literal in `new`:** `Self { feld: wert, … }` ohne Semikolon als Rückgabewert, alle Felder müssen angegeben werden.
- **`while let Some(x) = v.pop()`** leert einen Stack idiomatisch, ohne `unwrap` und ohne Längenzähler.
- **`unwrap()` bei garantierten Vorbedingungen:** Hier vertretbar, weil die Aufgabe nur gültige Aufrufe zusichert. Außerhalb von LeetCode würde man eher `Option<i32>` zurückgeben, wie `Vec::pop` selbst.
- **Namen beschreiben Garantien, nicht Mechanik:** `ensure_front` statt `umkippen`, sobald die Methode nur noch bei Bedarf kippt.
