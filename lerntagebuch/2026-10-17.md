# Lerntagebuch – 2026-10-17

## 1354. Construct Target Array With Multiple Sums (Hard)

- **Muster:** Rückwärts denken + Max-Heap; wiederholtes Abziehen per Modulo zusammenfassen
- **Hinweisstufe benötigt:** 1 (Beobachtungs-Hinweis bei der Sonderregel `rest == 1`; Algorithmus sonst über Gegenfragen und Gegenbeispiele selbst erarbeitet. Bei der Komplexitätsanalyse Stufe 1 mit der Tabelle „Ergebnis < max/2“, die Funktion log₂ wurde auf Nachfrage genannt.)
- **Komplexität:** Zeit O(n · log M · log n) mit M = größter Wert (≤ 10⁹, log M ≈ 30), Speicher O(n)
- **Status:** lokale Tests grün (10 Tests), Einreichung offen
- **Wiederholen am:** 2026-10-20, dann 2026-10-24, dann 2026-11-17

### Aufgabe

Start ist ein Array `arr` aus `n` Einsen. Ein Schritt: `x` = Summe aller Elemente, dann einen beliebigen Index `i` auf `x` setzen (beliebig oft, auch mehrfach derselbe Index). Kann man `target` erreichen?

**Constraints:** `1 <= n <= 5 * 10^4`, `1 <= target[i] <= 10^9`

Beispiele: `[9,3,5]` → true, `[1,1,1,2]` → false, `[8,5]` → true. Eigene Testfälle: `[1, 10^9]` → true, `[2,4]` → false, `[3,3,3]` → false, `[5]` → false, `[1]` → true, `[1,1,1]` → true, `[10^9; 3]` → false (Overflow-Test).

### Kernidee (eigene Worte)

> Die Kernidee ist es, das Target-Vector in einen Heap umzuwandeln und nicht von Anfang nach Ende zu schauen, sondern zu schauen, ob das Target/Ende zu einem Anfang werden kann. Dafür wird immer das größte Element aus dem Heap genommen, da dies als letztes erstellt wurde in Target, und für dieses geprüft, ob es gebildet werden konnte. Dort muss man dann einige Randfälle abfangen und dann den neuen Wert bilden, aus dem sich der größte gebildet hat, und diesen zurück in den Heap geben.

**Schärfung:** Der Kern ist das Rückwärtsdenken: Vorwärts gibt es viele Wege, rückwärts ist der Vorgänger eindeutig (`alt = max − rest`). Der Heap ist nur das Werkzeug, um das Maximum schnell zu finden. Im Satz fehlt das **Modulo** (`alt = max % rest`), ohne das die Lösung bei `[1, 10^9]` rund 10⁹ Schritte braucht. Erst dadurch halbiert jeder Schritt den Wert mindestens.

### Weg zur Lösung

1. **Erster Ansatz:** Min-Heap, vorwärts vom kleinsten Target-Element aus prüfen, ob es aus der aktuellen Summe gebildet werden kann. Frage: Darf man Indizes mehrfach ersetzen? Ja.
2. **Vorwärts von Hand an `[8,5]`:** `[1,1]→[2,1]→[3,1]→[4,1]→[4,5]→[9,5]` scheitert, `[1,1]→[1,2]→[3,2]→[3,5]→[8,5]` klappt. Erkenntnis: Vorwärts gibt es zu viele Verzweigungen.
3. **Rückwärts lesen:** Der Vorgänger ist immer eindeutig. Regel selbst gefunden: Das größte Element wurde zuletzt geschrieben, alter Wert = `max − (summe − max)`. An `[9,3,5]` bis `[1,1,1]` durchgerechnet.
4. **Abbruch:** `[1,1,1,2]` → `2 − 3 = −1 < 1` → false.
5. **Laufzeitfalle:** `[1, 10^9]` braucht ~10⁹ Schritte. Erkannt, dass die Rest-Summe gleich bleibt → „etwas, wo nur der Rest rauskommt“ → Modulo. Erst `summe % max` und `rest = …` vertauscht, dann `max % rest`.
6. **Randfälle durch Modulo:** `rest == 1` → true (Modulo liefert 0, aber man trifft die 1 vorher; hier Stufe-1-Hinweis gebraucht). `[3,3,3]`: `3 % 6 = 3` → Endlosschleife → `max < rest` → false. `n == 1`: `rest = 0` → Division durch 0 abfangen.
7. **Code:** Erste Fassung ohne `max == 1 → true` (Trace an `[1,1,1]` zeigte den Fehler) und mit `i32`-Summe (Overflow). Danach alles einmal am Anfang auf `i64` gemappt, `neu == 0` explizit abgefangen, `while let` durch `loop` ersetzt.
8. **Komplexität:** Speicher O(n) und O(log n) pro Durchlauf sofort richtig. Die Anzahl der Durchläufe war schwer: `max % rest < max / 2`, also kann jedes Element höchstens log₂ M mal getroffen werden.

### Meine Lösung

Erste lauffähige Fassung (alle Tests grün):

```rust
impl Solution {
    pub fn is_possible(target: Vec<i32>) -> bool {
        let target_i64: Vec<i64> = target.iter().map(|&x| x as i64).collect();
        let mut sum: i64 = target_i64.iter().sum();
        let mut heap: BinaryHeap<i64> = BinaryHeap::from(target_i64);
        while let Some(max) = heap.pop() {
            let rest = sum - max;
            if max == 1 {
                return true;
            }
            if rest == 1 {
                return true;
            }
            if rest <= 0 {
                return false;
            }
            if max < rest {
                return false;
            }
            let neu = max % rest;
            heap.push(neu);
            sum -= max - neu;
        }
        true
    }
}
```

Endfassung nach dem Review:

```rust
impl Solution {
    pub fn is_possible(target: Vec<i32>) -> bool {
        let target_i64: Vec<i64> = target.iter().map(|&x| x as i64).collect();
        let mut sum: i64 = target_i64.iter().sum();
        let mut heap: BinaryHeap<i64> = BinaryHeap::from(target_i64);
        loop {
            let max = heap.pop().unwrap();
            let rest = sum - max;
            if max == 1 {
                return true;
            }
            if rest == 1 {
                return true;
            }
            if rest <= 0 {
                return false;
            }
            if max < rest {
                return false;
            }
            let neu = max % rest;
            if neu == 0 {
                return false;
            }
            heap.push(neu);
            sum -= max - neu;
        }
    }
}
```

Unterschied: Der Fall `neu == 0` wird jetzt direkt abgefangen statt indirekt über `rest <= 0` im nächsten Durchlauf. Das unerreichbare `true` nach der Schleife entfällt durch `loop`.

Offene Ideen: `if`s mit gleichem Rückgabewert per `||` zusammenfassen; `.expect("heap never empty")` statt `.unwrap()`.

### Wo ich hing

- Am Anfang die Annahme, jede Zahl entstehe in einem Schritt direkt aus der Summe (Vorwärtsdenken).
- Sonderregel `rest == 1`: Der Unterschied zwischen `[1, 10^9]` und `[2,4]` (beide Modulo 0) war nicht greifbar. Erst die direkte Beobachtung half.
- Modulo-Operanden zunächst vertauscht (`summe % max`).
- `max == 1 → true` stand im Algorithmus, fehlte aber im Code.
- Komplexität: Dass Modulo den Wert mindestens halbiert, und daraus log M als Schrittzahl abzuleiten.

### Rust-Learnings

- `BinaryHeap` ist standardmäßig ein **Max-Heap**, passt hier ohne `Reverse`.
- **Overflow:** Eine Summe von 5·10⁴ × 10⁹ passt nicht in `i32`. Im Debug-Build führt das zum Panic `attempt to add with overflow`.
- `iter().sum() as i64` addiert erst und castet danach, der Overflow passiert also trotzdem. Besser ist, einmal am Anfang per `.map(|&x| x as i64).collect()` (oder `i64::from`) zu konvertieren. Dann ist im Schleifenkörper kein Cast nötig.
- Rust addiert/vergleicht keine gemischten Typen (`i64 - i32` → E0277/E0308).
- `%` durch 0 führt zu einem Panic, der Fall muss vorher abgefangen werden.
- `loop` ohne `break` hat den Typ `!` (never type), der sich in jeden Typ umwandeln lässt. Deshalb braucht die Funktion nach der Schleife keinen Rückgabewert (Rust Book, Kap. 19.4). Es liegt nicht am `if`.
- Toter Code nach `while let`, wenn der Heap nie leer wird: Alternativ ließe sich `unreachable!()` verwenden.
